# Locust baseline — 20 сентября 2026

Стенд: локальный Minikube, одна реплика Backend, Gunicorn с двумя sync workers и
двумя threads, запрос `GET /api/v1/events/` через `kubectl port-forward`. Между
запросами каждого пользователя — случайная пауза 0,5–1,5 секунды. Каждый прогон после
набора пользователей длился до одной минуты.

| 10 | 243 | 0 | 133 ms | 150 ms | 4.81 s | 8.34 | 6m CPU / 86 MiB |

| 200 | 4932 | 572 (11.60%) | 1.36 s | 5.70 s | 10.0 s | 82.55 | 137m CPU / 136 MiB |

Максимальная проверенная ступень, удовлетворяющая обоим условиям задания, — 100
одновременных пользователей: ошибок нет, среднее время ответа значительно меньше
5 секунд. При 150 пользователях появились ошибки соединения, поэтому эту ступень уже
нельзя считать корректно обработанной, хотя среднее время успешных ответов оставалось
низким. На 200 пользователях очередь запросов привела к timeout и падению throughput.

Это предел конкретного сценария с прогретым Redis-кешем и локальным port-forward,
а не всего API. Для защиты тест следует повторить через Ingress с теми же параметрами.
По пику на успешной ступени Backend получает request 250m CPU / 192Mi RAM и limit
500m CPU / 384Mi RAM. HPA target 60% CPU начнёт масштабирование примерно при 150m
среднего CPU на реплику.

## Проверка через Locust Operator и HPA

При первом запуске 150 пользователей через внутрикластерный Service HPA увеличил
Backend с одной до двух реплик. Получено 3741 запросов, 108 ошибок соединения (2,89%),
медиана 22 мс, p95 1,0 с и около 95 RPS. На повторном прогретом запуске с уже готовыми
репликами получено 7829 запросов, 87 ошибок соединения (1,11%), медиана 4 мс, p95
610 мс, среднее 100 мс и около 126 RPS. Прогрев заметно улучшил задержки и throughput,
но безошибочной подтверждённой ступенью остаются 100 пользователей.
